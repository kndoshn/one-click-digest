# Article Summarizer Chrome Extension 設計書 v1.1-UX（UX改善版）

- 作成日: 2026-01-11
- 前提: v1.0 設計（MV3 / 右上パネル / 4モード / Token見積 / 全文分割 / $1.00上限 / prompt caching）
- この文書の焦点: **UX（待ち時間、理解しやすさ、安心感、操作ミスの減少）**のための改善

---

## 1. 定義

### 1.1 UX設計の目的
- ユーザーが「何が起きているか」「どれくらい待つか」「いくらかかるか」を迷わず理解できる。
- クリックから結果表示までの体感を速くする（実時間ではなく **体感速度**）。
- 誤操作（閉じてしまう、想定外の課金、要約できないのに待たされる）を減らす。

### 1.2 改善の前提条件（仕様として固定）
- Done画面で Mode / 言語を変えたら **常に最初から再実行（抽出→見積→承認→map→reduce）**
- 推定コストのハード上限 **$1.00** は **reduce2（フォーマット修正）も含めた最悪ケース**で判定する
- UIは「右上パネル」＋「簡易ローディング」を基本とする（過度に派手にしない）

---

## 2. 要点（UX改善の骨子）

### 2.1 “最短1クリック”の起動体験（迷わせない）
- パネルを開いた瞬間に、上部に **4つのモードボタン**を並べる（選ぶ=開始）。
- 既定モード（Optionsで設定）を **強調表示**し、ユーザーは多くの場合「そのままクリック」できる。

### 2.2 待ち時間の“分解表示”（簡易だが安心させる）
- ローディング文言はシンプルにしつつ、1行だけステータスを追加:
  - `記事を解析中…`
  - `見積を計算中…`
  - `要約作成中…（2/8）`
- これにより「止まっているのか」「まだ動いているのか」が分かる。

### 2.3 承認UIを“意思決定しやすく”（情報は全部出すが押し付けない）
- 承認カードは「概要→詳細」の2層:
  - 概要: 文字数 / 推定コスト（レンジ） / 推定時間（レンジ）
  - 詳細（折りたたみ）: 推定入力トークン / 推定出力トークン / chunk数 / モデル内訳
- `実行` ボタンの隣に `軽量モードで実行`（例: 3行）を置き、迷ったら安く済む導線を用意。

### 2.4 エラー/失敗を“次の行動”に変換
- エラーメッセージは「原因」より「ユーザーが今できること」を主語にする:
  - APIキー未設定: `設定画面を開く`
  - 抽出失敗: `別のページで試す / リロードして再試行`
  - $1超過: `より短いモードに変更 / 抽出範囲を短くする（オプション）`

### 2.5 Copy体験を“完了”として気持ちよく
- Copy後に小さなトースト `コピーしました`（2秒で消える）
- Copyボタンは Done状態で常に固定位置（右下）に表示（スクロールしてもすぐ押せる）

## 3. 比較（v1.0 → v1.1-UXで何が変わるか）

### 3.1 起動導線
- v1.0: 何となくモード選択→開始（UIの自由度が高い分、迷う可能性）
- v1.1-UX: **モードボタン=開始**（最短、迷いにくい）

### 3.2 待ち時間表示
- v1.0: 「要約作成中…」のみ
- v1.1-UX: 「要約作成中…」は維持しつつ **1行ステータス＋（必要なら）進捗 x/y**

### 3.3 承認UI
- v1.0: 情報を全表示（過情報になりやすい）
- v1.1-UX: **概要→詳細**で段階開示（初心者にも優しい）

### 3.4 Done画面の再実行（仕様固定だがUX改善）
- 仕様: Mode/言語変更は常にフル再実行（固定）
- 改善: 変更操作後、前回結果をすぐ消さずに「更新中」ラベルで残す（読みながら待てる）

## 4. 具体設計（UX仕様）

## 4.1 右上パネルの情報設計（IA）

### 4.1.1 ヘッダ（固定）
- タイトル: `要約`
- 右端: `×`（閉じる）
- 2行目（小さめ）: `このページを要約します` + 省略URLドメイン（例: `example.com`）

### 4.1.2 コントロール行（固定）
- 言語セレクタ: `Auto` + Accept-Language リスト
- 右端: `設定`（Optionsを開くリンク）
  - APIキー未設定時は `設定（APIキー未設定）` のように赤点/バッジ

### 4.1.3 メイン領域（状態で切替）
- Idle: モード選択ボタン（4つ）
- Extracting/Preflight/Summarizing: ローディング + ステータス + 取消ボタン（または×に統合）
- Confirming: 承認カード（概要→詳細）
- Done: 要約本文 + Copy + 再実行（モード/言語変更を促すUIは置かない。変更は上部で行い、変更したら自動的に新Run開始）

### 4.1.4 フッタ（固定）
- Done時: `Copy`（primary） / `閉じる`（secondary）
- その他: `キャンセル`（処理中のみ）

## 4.2 ワイヤーフレーム（テキスト）

### 4.2.1 Idle（初期）
```
┌───────────────────────────┐
│ 要約                      ×│
│ example.com                │
│ 言語: [Auto v]   [設定]     │
├───────────────────────────┤
│ どの形式で要約しますか？     │
│ [ 3行 ]  [ 5行 ]           │
│ [10行 ]  [TL;DR+12+結論]    │
│ （クリックで開始）          │
└───────────────────────────┘
```

### 4.2.2 Preflight（承認不要の場合は短時間で通過）
```
│ 見積を計算中…              │
│ 推定コスト: $0.08〜$0.15    │
│ 推定時間: 10〜25秒         │
```

### 4.2.3 Confirming（承認カード）
```
┌ 見積と承認 ─────────────────┐
│ 文字数: 42,500              │
│ 推定コスト: $0.35〜$0.80     │
│ 推定時間: 25〜70秒          │
│ [詳細 v]                    │
│  - 推定入力: 18k tokens     │
│  - 出力上限: 900 tokens     │
│  - チャンク: 8              │
│  - モデル: map=Haiku / reduce=Sonnet │
│ [実行] [軽量モードで実行(3行)] [キャンセル] │
└───────────────────────────┘
```

### 4.2.4 Summarizing（簡易だが“動いている”）
```
│ 要約作成中…                 │
│ 進捗: 2/8（チャンク要約）    │
│ 推定残り: 20〜50秒           │
│ [キャンセル]                │
```

### 4.2.5 Done（Copyがすぐ押せる）
```
│ 要約（10行）                │
│ - ...                       │
│ - ...                       │
│ ...                         │
│                              │
│ [Copy]  （コピーしました）   │
└───────────────────────────┘
```

## 4.3 主要ユーザーフロー（UX観点）

### 4.3.1 標準（短〜中記事）
1) アイコンクリック → パネル即表示（Idle）  
2) 4モードから1つクリック → Extracting  
3) Preflight（概算→精算で更新。承認不要なら自動でSummarizingへ）  
4) Done表示 → Copy → Close

**UX狙い:** “考える前に押せる”、待つ理由が見える。

### 4.3.2 長文（承認あり）
1) モードクリック → Extracting  
2) Preflightで概算表示（即）  
3) Token Count成功で見積更新（必要なら承認カードへ遷移）  
4) Confirmingで `実行` / `軽量モード` / `キャンセル`  
5) Summarizing（進捗 1/8…）  
6) Done → Copy

**UX狙い:** 課金/時間に納得してから進められる。

### 4.3.3 Mode/言語変更（仕様: フル再実行）
- ユーザーが上部で Mode/言語を変更すると、即座に「新しいRunを開始します」トーストを表示し、**前回結果を薄く残しつつ** Summarizing状態へ遷移する（※古い結果と混同しないよう “前回結果（更新中）” ラベルを付ける）。
- 完了したら新結果に置き換える。

**UX狙い:** 待ち時間の間に前回結果を読める。空白時間を減らす。

## 4.4 マイクロコピー（文言）設計

### 4.4.1 成功/進捗
- `記事を解析中…`
- `見積を計算中…`
- `要約作成中…`
- `コピーしました`

### 4.4.2 承認
- タイトル: `見積と承認`
- 注意: `この記事は長文のため、要約に時間とコストがかかる可能性があります。`

### 4.4.3 要約しない（抽出が不適）
- `本文を十分に抽出できませんでした（記事ページではない可能性があります）`
- `本文が短いため要約は作成しません（約 {n} 文字）`
- `本文が要約に不向きな形式の可能性があります（リンクやUI文言が多い）`

### 4.4.4 失敗（次アクション付き）
- APIキー未設定:
  - `APIキーが未設定です。設定画面で入力してください。`
  - ボタン: `設定を開く`
- 認証エラー:
  - `APIキーが無効の可能性があります。設定を確認してください。`
- ネットワーク:
  - `通信に失敗しました。ネットワークを確認して再試行してください。`
  - ボタン: `再試行`
- ハード上限超過:
  - `推定コストが上限（$1.00）を超えます。短いモードを選ぶか、記事の長さを減らしてください。`
  - ボタン: `3行で実行`（コストを下げる導線）

## 4.5 アクセシビリティ（最低限だが効く）

- キーボード:
  - Tabで操作可能（フォーカストラップをパネル内に限定）
  - Enterで「選択中のモードを実行」
  - Escで閉じる（処理中はキャンセル確認）
- スクリーンリーダ:
  - `aria-live="polite"` で進捗テキストを読み上げ可能にする
  - ボタンに適切なラベル（例: `Copy summary to clipboard`）
- 視認性:
  - 12〜14px以上、行間 1.4〜1.6
  - コントラスト確保（サイト背景に埋もれない）
- クリック領域:
  - ボタンは最低 40px 高さ（誤タップ低減）

---

## 4.6 体感速度を上げる実装ガイド（UXのための実装制約）

### 4.6.1 “すぐ出す”
- アイコンクリック → まず空のパネルを即表示（100ms以内を目標）
- 重いReadabilityは表示後に開始（パネル内で「解析中…」を出す）

### 4.6.2 “止めない”
- Readabilityが重い場合、`requestIdleCallback` / 分割処理でメインスレッドブロッキングを避ける（可能な範囲で）
- 長文のchunkingは段落境界処理でコストを抑える（正規表現の過剰使用を避ける）

### 4.6.3 “戻れる”
- 全フェーズに `キャンセル` を用意（ただし Idle では不要）
- キャンセル時は `キャンセルしました` を明示し、すぐIdleへ戻す

---

## 4.7 UXのためのデータ保持（最小）
※「Mode/言語変更はフル再実行」の仕様を守りつつ、UXだけ改善するための保持です。

- **前回の要約結果**（表示のためだけ）: パネルが開いている間メモリ保持（storageに永続化しない）
- **前回の見積**: 同上（ユーザーの意思決定に役立つ）
- **平均所要時間（EMA）**: storageに保存しても良い（個人端末内。プライバシー影響小）  
  - 目的: 予想時間表示の精度向上

## 5. 受け入れ基準（UX QAチェックリスト）

### 5.1 起動/基本操作
- [ ] クリックで必ず右上パネルが表示される（サイトCSSに負けない）
- [ ] 初回でも迷わずモード選択→開始できる
- [ ] APIキー未設定時は設定導線が明確

### 5.2 待ち時間
- [ ] 解析/見積/要約のステータスが最低1行で更新される
- [ ] 15秒以上の処理は進捗（x/y）か残り目安が出る

### 5.3 コスト/承認
- [ ] 承認カードに「文字数/トークン/コスト/時間」が出る
- [ ] $1.00超過時は実行できず、代替（短いモード）導線がある
- [ ] 変更後に見積が更新される（概算→精算）

### 5.4 コピー/完了
- [ ] Copy後にフィードバックが出る（トースト）
- [ ] スクロール位置に関係なくCopyが押せる（固定ボタン）

### 5.5 例外
- [ ] 通信エラーは再試行導線がある
- [ ] 抽出不適合は「要約しない」判断が速く、理由が分かる
- [ ] キャンセルは即時反映され、ユーザーに分かる

## 6. 追加の不明点（UX改善の最終調整用）
※設計をこれ以上“無駄に複雑化”させないため、UXに直結するものだけ挙げます。

1) 進捗表示をどこまで出すか  
- A: 文字だけ（解析中/要約中…）  
- B: 文字 + `x/y`（チャンク数だけ）  
- C: B + 残り時間（EMAで推定）

2) 承認UIのボタン構成  
- A: `実行` / `キャンセル` のみ（最小）  
- B: A + `軽量モードで実行`（推奨）

## 結論要約
- v1.1-UXは、仕様（フル再実行、$1上限）を守ったまま、**迷いの削減・待ち時間の安心・課金の納得・コピー完了感**を強化する設計です。  
- 特に効果が大きいのは「モードボタン=開始」「待ち時間を3段階で見せる」「承認UIの段階開示」「前回結果を残して更新中にする」の4点です。
